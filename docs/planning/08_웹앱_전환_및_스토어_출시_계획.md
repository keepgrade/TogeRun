# 웹앱 전환과 스토어 출시 계획 (초안)

TogeRun을 러너블(runable.me)처럼 **앱 구조의 웹앱**으로 다시 짜고, 이어서 Google Play와 App Store에 출시하는 단계 계획입니다. 코드 작성 전 기획 단계 문서이며, 규정·금액은 출시 시점에 공식 문서로 다시 확인해야 합니다.

## 1. 목표와 전제

- 목표: ① 모바일에서 앱처럼 쓰는 웹앱 ② 홈 화면에 설치되는 PWA ③ 스토어 앱(Android·iOS)
- 지금 상태: 서버 없는 프런트엔드 PoC(Next.js, 데이터는 브라우저 localStorage). 기능은 대회·버디·리뷰·커뮤니티·프로필·알림·캘린더·지도가 있습니다.
- 전제: 개발은 1인에 가깝고 React·Next 코드가 이미 있습니다. 결제 중개가 없어서 인앱결제 심사 부담은 없습니다.

## 2. 가장 먼저 정할 기술 방향

| 안 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| **A. 웹앱 + Capacitor 래핑 (권장)** | 웹앱을 만들고 Capacitor로 Android·iOS 앱에 담는다 | 코드 한 벌로 세 곳(웹·Android·iOS) 출시. 푸시·공유·사진 같은 기기 기능을 플러그인으로 사용 | 완전한 네이티브보다 움직임이 덜 부드러울 수 있음 |
| B. PWA + TWA | PWA를 Google Play에 등록 | 가장 쉬움 | **iOS는 PWA만으로 스토어에 올릴 수 없음** |
| C. React Native(Expo) 재작성 | 앱을 새로 작성 | 네이티브 느낌 | 웹 코드 재사용이 작고 시간이 큼 |

권장은 **A**입니다. 나중에 성능이 문제가 되면 일부 화면만 네이티브로 바꿀 수 있습니다.

A안에서 지금 알아 둘 제약:
- 스토어 앱에는 웹 자산을 앱 안에 넣는 방식(정적 빌드)이 안전합니다. 웹사이트를 그대로 띄우기만 하는 앱은 Apple이 "최소 기능 미달(4.2)"로 반려할 수 있어서, 푸시 알림·캘린더 추가·사진 선택 같은 **기기 기능을 실제로 써야** 합니다.
- 정적 빌드를 쓰면 `/races/[id]` 같은 동적 경로를 미리 만들 수 없어서, **상세 화면은 쿼리 방식(`/race?id=`)이나 클라이언트 라우팅**으로 설계해야 합니다. 이 결정을 1단계에서 해야 나중에 다시 뜯지 않습니다.
- 검색엔진 노출(SEO)이 필요하면 서버 렌더링이 필요합니다. MVP는 **앱 우선(SEO 없음)**으로 가고, 필요해지면 공개용 소개·대회 페이지를 따로 둡니다.

## 3. 단계별 계획

크기는 S(며칠), M(1~2주), L(3주 이상)의 대략치입니다.

### 0단계. 결정과 준비 (S)
- 기술 방향(A안)과 상세 화면 라우팅 방식 확정
- 앱 이름·식별자 확정(`TogeRun`은 가칭. 상표·스토어 이름 중복 확인), 패키지 ID 예: `kr.togerun.app`
- 개발자 계정 준비: Apple Developer Program(연 $99, 개인 또는 사업자), Google Play Console(1회 $25). 계정 유형에 따라 인증 절차가 다름
- 인스타그램 로그인 같은 로그인 수단 방침 확정(5장 참고)

### 1단계. 앱 구조로 화면 틀 바꾸기 (M) — 웹에서 먼저
러너블의 구조를 참고합니다.
1. **하단 탭 5개**: 홈, 대회(목록·캘린더·지도를 위쪽 탭으로 묶음), **가운데 "버디 구하기" 버튼**, 커뮤니티, 마이. 알림은 위쪽 종 아이콘으로 이동
2. **화면마다 제목줄과 뒤로가기**, 모바일 안전 영역(노치·홈 바) 처리
3. **홈을 피드로**: 히어로·푸터·뉴스레터 같은 마케팅 구획을 걷어내고 검색, 내 관심 대회 D-day, 접수 임박, 모집 중인 버디 중심으로 재구성. 소개·정책 링크는 마이로 이동
4. **필터는 아래에서 올라오는 시트**, 대회 상세는 **하단 고정 버튼**(관심 저장 / 버디 구하기)
5. **화면 상태를 주소에 담기**: 지금 쓰는 `sessionStorage` 전달값(검색어, 상태, 종류·범위, 탭)을 쿼리 파라미터로 바꿔서 뒤로가기·공유·앱 딥링크가 되게 함
6. 데스크톱은 따로 정할 것(넓은 격자 유지 또는 가운데 좁은 열)

### 2단계. 데이터 계층 분리 (M) — 서버 붙일 준비
- 화면이 `localStorage` 저장소를 직접 쓰는 구조를 **데이터 접근 계층(repository)** 뒤로 숨깁니다. 이후 서버 API로 바꿀 때 화면은 그대로 둡니다.
- 로딩·오류·빈 화면 상태, 낙관적 갱신, 오프라인 안내를 공통 패턴으로 정리
- 지도: 지금의 OpenStreetMap 공개 타일은 상용 앱에서 쓰기 어려우므로 **상용 지도 제공자(카카오·네이버 지도 SDK 또는 유료 타일)로 교체 검토**

### 3단계. PWA 만들기 (S)
- 웹 앱 매니페스트, 아이콘, 스플래시, 설치 안내, 서비스 워커로 정적 자산 캐시
- 오프라인에서도 저장한 관심 대회와 최근 본 목록은 보이게 함
- iOS의 웹 푸시는 홈 화면에 설치한 PWA에서만 되는 제약이 있음

### 4단계. 백엔드와 계정 (L)
- 인증(카카오·Google·네이버 + 애플 로그인), 계정 삭제
- DB와 API: `docs/planning/05_데이터모델.md`의 대회, 모집글, 리뷰, 커뮤니티, 신고, 알림, 프로필
- 파일 저장(기록 인증 사진, 확인 뒤 삭제), 푸시 알림 발송, 운영자 콘솔(대회 입력·신고 처리·기록 인증 승인)
- 선택지: 관리형 서비스(Supabase·Firebase)로 빠르게 시작 또는 직접 서버 구축. 1인 개발이면 관리형을 권장
- **대회 데이터 확보 방식**이 가장 큰 제품 위험입니다. 크롤링은 저작권·약관 문제가 있으므로 공식 자료 직접 입력, 주최 측 제휴, 사용자 제보 등을 정해야 함

### 5단계. 앱 래핑과 기기 기능 (M)
- Capacitor 프로젝트 생성, Android·iOS 빌드
- **네이티브 기능 연결**: 푸시 알림(FCM·APNs), 딥링크(공유한 대회·모집글 링크 열기), 공유 시트, 캘린더 추가, 사진 선택(기록 인증), 위치(내 주변 대회), 상태 표시줄·스플래시, Android 뒤로가기 처리
- 앱 아이콘·스플래시 제작, 버전·빌드 번호 정책, 앱 안 업데이트 방식(웹 자산 갱신 가능 범위 확인)

### 6단계. 스토어 심사 준비와 베타 (M)
- 스토어 자료: 아이콘, 스크린샷, 설명, 개인정보처리방침 주소, 이용약관, 지원 연락처, 연령 등급
- 내부 테스트(Play 내부 테스트, TestFlight) 후 소수 사용자 베타
- Google 개인 개발자 계정은 신규 계정에 비공개 테스트 요건이 있을 수 있으니 **계정 생성 직후 요건 확인**

### 7단계. 출시와 운영 (지속)
- 단계적 출시, 충돌·오류 수집, 분석 도구, 사용자 문의 대응, 신고 처리 운영 시작
- 대회 일정 갱신 루틴(시즌별), 푸시 알림 시점 조정

## 4. 스토어 심사에서 걸리기 쉬운 항목

TogeRun은 **사용자가 글을 올리는 서비스**라서 아래를 미리 갖춰야 합니다.
- **사용자 콘텐츠 정책(Apple 1.2, Google UGC)**: 신고, 차단, 약관 동의, 운영자 처리 연락처 → 이미 신고·차단은 구현되어 있음
- **계정 삭제**: 앱 안에서 계정과 데이터를 삭제할 수 있어야 함(Apple·Google 공통)
- **소셜 로그인**: iOS에서 카카오·구글·네이버를 쓰면 **애플로 로그인** 또는 동등한 수단 제공이 필요할 수 있음
- **개인정보 표기**: Apple의 앱 개인정보 라벨, Google의 데이터 보안 양식. 수집 항목(성별·나이·러닝 기록·이메일)을 정확히 기재
- **최소 기능(Apple 4.2)**: 웹페이지 감싸기만 하면 반려 위험 → 5단계의 네이티브 기능이 필수
- **위치 정보**: 서버로 위치를 수집·저장하면 한국의 위치정보 관련 신고·고지 의무를 확인해야 함. 기기 안에서만 쓰면 부담이 작음
- **미성년자**: 연령 등급과 14세 미만 가입 제한 방침 필요
- **인스타그램 로그인**: Meta 정책상 일반 개인 계정으로는 로그인할 수 없으므로 앱 로그인 수단으로 두지 않고 **인스타그램은 팔로우·공유 링크로만** 사용

## 5. 지금 코드에서 바뀌어야 하는 부분

| 현재 | 바꿀 방향 |
| --- | --- |
| `AppShell` 상단 메뉴 + 6개 탭 + 푸터 | 5개 탭 + 가운데 버튼 + 제목줄 |
| 마케팅형 긴 홈 | 피드형 홈(소개·정책은 마이로) |
| `sessionStorage`로 화면 간 값 전달 | 주소 쿼리 파라미터 |
| `localStorage` 저장소(`lib/store.tsx`) | 데이터 접근 계층 → API |
| `/races/[id]` 동적 경로 | 정적 빌드에 맞는 라우팅 |
| OpenStreetMap 타일 | 상용 지도 |
| `<input type=file>` 모의 인증 | 기기 사진 선택 + 업로드 |
| `.ics` 내려받기 | 기기 캘린더 추가 |
| 모의 로그인 버튼 | 실제 OAuth + 애플 로그인 |

## 6. 결정된 것과 남은 것

결정됨 (2026-10-23)
- **PC에서도 앱을 그대로 쓴다.** 러너블처럼 PC에서는 폭 480px의 가운데 열로 앱이 동작하고, **서비스 소개 랜딩페이지는 `/about`에 따로 둔다**("서비스 소개" 메뉴에서 연다). 앱 화면은 모바일 한 열 레이아웃만 만든다.
- **러너블처럼 가운데 좁은 열**의 앱 구조로 간다(하단 탭 5개).
- **가운데 버튼은 "버디 구하기"**: 대회를 고르고 모집글을 쓰는 흐름으로 바로 이어진다.
- **서버는 가비아 클라우드**: 관리형 서비스가 아니라 직접 서버를 구축한다(4단계에서 API 서버·DB·파일 저장·푸시 발송을 직접 구성. 운영·보안·백업 책임이 따른다).
- **먼저 웹앱을 만든다**(1~3단계).

추후로 미룸
- 대회 데이터 확보: 네이버 검색 API 등을 쓰는 방식(주의: 검색 API는 대회 일정·참가비 같은 구조화된 데이터를 주지 않아서 별도 정리·검수가 필요할 수 있음)
- 계정 명의(개인 vs 사업자)와 스토어별 출시 순서
- SEO가 필요한 시점

## 7. 제안하는 진행 순서

`0단계 결정` → `1단계 화면 틀(웹)` → `2단계 데이터 계층` → `3단계 PWA` 여기까지가 **웹앱 출시 가능선**입니다. 이후 `4단계 서버·계정` → `5단계 앱 래핑` → `6단계 심사 준비` → `7단계 출시`로 갑니다. 1~3단계는 서버 없이 지금 바로 진행할 수 있고, 4단계 이후부터 대회 데이터 확보와 계정 비용 같은 외부 결정이 필요합니다.
